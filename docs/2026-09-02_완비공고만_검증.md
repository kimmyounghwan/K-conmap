# 「값이 다 있는 공고만 계산한다」 — 결정과 검증

작성 2026-09-02 · 대상: 바로투찰 / 공고 목록

## 1. 무엇을 바꿨나

### 공고 목록 (`/live`)
- **바로투찰 버튼을 «계산되는 공고»에만 답니다.**
  - 조건 ① 아직 마감 전 (마감된 공고는 투찰 자체가 안 됨)
  - 조건 ② `isReady(r)` — 기초금액 · 낙찰하한율 · A값 · 예비가격 정보가 **전부** 있음
- 조건에 못 미치는 공고는 버튼 대신 **왜 안 되는지**를 적습니다.
  («조달청 자료에 «낙찰하한율» 이 아직 안 실려 왔습니다. 30분마다 다시 받아옵니다.»)
- 판정 함수는 바로투찰과 **같은 것**을 씁니다 (`BaroBid.jsx` 의 `missingOf` / `isReady` 를 export).
  따로 두면 반드시 어긋납니다.

### 바로투찰 (`/`)
- 공고 고르는 칸은 기본으로 **계산되는 공고만** 보여줍니다 («그래도 보기» 로 전환 가능).
- 값이 덜 갖춰진 공고를 고르면 **금액을 내지 않고** 무엇이 빠졌는지 ✓/✕ 로 알려줍니다.

## 2. 왜 이렇게 했나

버튼을 눌렀는데 «계산할 수 없습니다» 가 뜨면 도와준 게 아니라 헛걸음을 시킨 것입니다.
그리고 없는 값을 추측해서 금액을 내밀면 **수천만원이 어긋납니다** (2026-09-02 기록 §9).
반쯤 아는 걸로 답을 내미는 것보다, 모른다고 말하는 편이 낫습니다.

실측(2026-09-02, 마감 전 공고 1,939건):

| 항목 | 건수 |
|---|---|
| 네 값이 다 있음 (**완비**) | **860건 (44.4%)** |
| 기초금액 있음 | 1,535 |
| 낙찰하한율 있음 | 1,071 |
| A값 있음 | 1,500 |
| 예비가격 정보 있음 | 1,057 |

## 3. 「얼마나 차이가 나는가」 — 실제 개찰로 검증

**표본** 2026-04 ~ 09 개찰 중 *기초금액 + A값 실측* 이 다 있는 1,118건.
그중 낙찰하한율을 낙찰자 금액에서 되짚어 **확정한 958건** 으로 검증했습니다.

되짚는 방법: `낙찰하한율 = (낙찰가 − A) / (예정가격 − A) × 100`
→ 89.745 에 710건, 88.745 에 31건, 87.495 에 5건으로 **또렷하게 뭉칩니다.**
낙찰하한금액 공식 `(예정가격 − A) × 하한율 + A` 가 실제와 맞는다는 확인입니다.

### 예정가격 분포도 이론과 맞습니다

| 예가범위 | 이론 표준편차 | 실측 표준편차 | 건수 |
|---|---|---|---|
| ±3% | 0.768 | **0.704** | 852 |
| ±2% | 0.512 | **0.495** | 106 |

### 지금 방식(사정률 75분위 + 0.3% 여유)의 성적

| 구간 | 건수 | 실격률 | 차이 중앙값 | 차이 평균 | 상위10% |
|---|---|---|---|---|---|
| 1억 미만 | 514 | 9.7% | **38.7만원** | 48.2만원 | 103만원 |
| 1~3억 | 303 | 13.5% | **131.9만원** | 142.6만원 | 269만원 |
| 3~10억 | 102 | 11.8% | **371.6만원** | 493.0만원 | 1,198만원 |
| 10억 이상 | 39 | 20.5% | 1,344만원 | 3,121만원 | 6,274만원 |
| **전체** | **958** | **11.6%** | **68.8만원 (0.87%)** | 237만원 | 346만원 |

→ 공고의 85%가 3억 미만입니다. 그 구간에서 실제 낙찰가와의 차이는
**수십만원 ~ 백몇십만원** 입니다. 「수천만원」은 사라졌습니다.

### 여유폭을 바꾸면 (958건 전체)

| 사정률 분위 | 여유 | 실격률 | 차이 중앙값 |

실격률과 차이는 **맞바꿈 관계**입니다. 사정률은 예측이 안 되는 난수라
(자기상관·요일·월·금액대·기관·같은날·재입찰 전부 유의하지 않음) 이 맞바꿈을
피할 방법은 없습니다. 지금은 «실격 1/9, 차이 0.87%» 자리에 두었습니다.

## 4. 완비 필터가 얼마나 도와주나

같은 958건을 «값이 없어 추정했을 때»(하한율 구간추정 + A값 5.07% 가정)로 돌리면
전체 차이 중앙값 73.5만원 · 실격 11.9% 로 **큰 차이가 없습니다.**
이유는 이 표본이 이미 «A값을 받아온 공고»라 완비에 가깝기 때문입니다.

구간규칙이 실제 하한율과 어긋난 경우는 1,118건 중 **7건(0.6%)** 뿐이었습니다.
즉 **완비 필터의 값어치는 정확도 향상이 아니라 «모르는 걸 모른다고 말하는 것»** 입니다.
하한율이 없는 공고(마감 전 1,939건 중 868건)에 대해 예전에는 구간규칙으로 찍었고,
그게 5억 공고에서 961만원 어긋난 사례가 있었습니다. 이제는 찍지 않습니다.

## 5. 검증 방법 (다시 돌릴 때)

1. 저장소를 얕게 받아 `data/extra_2026-0*.csv` 와 `data/store/first.json` 을 씁니다.
2. 기초금액·A값·투찰금액·투찰률이 다 있고 사정률이 95~105% 인 건만 남깁니다.
3. `낙찰하한율 = (낙찰가 − A)/(예정가격 − A) × 100` 로 하한율을 되짚어,
   후보값(89.745 / 88.745 / 87.495 / 87.745 / 86.745 / 85.495) 중
   **하나에만** 0 ~ +0.5%p 안으로 붙는 건만 씁니다.
4. 권장금액 `M = ceil( ceil((기초 × 사정률분위/100 − A) × 하한율/100 + A) × 1.003 )`
   를 실제 낙찰가와 비교합니다. `M < 실제 낙찰하한금액` 이면 실격입니다.

⚠️ `data/store/*.json` 은 저장소에 있는 건 **옛날 것**입니다.
   실제 수집 기록은 GitHub Actions 캐시에 있고, 저장소 사본에는 `llr`·`aval` 이 없습니다.
   화면용 최신 값은 배포된 `web/dist/data/bidindex.json` 에만 있습니다.

# 추가 (같은 날) — 채점을 바로투찰과 같은 계산으로 맞춤

## 7. 팀 검증에서 나온 사고 — 채점이 추천을 재현하지 못했다

팀원에게 958건으로 독립 검증을 시켰더니 **채점이 바로투찰과 다른 금액을 쓰고 있었습니다.**

| | 사정률 | 여유 | 예가범위 |
|---|---|---|---|
| 추천 화면 | P50 + 0.674σ (75분위) | ×1.003 | 그 공고의 값 |
| 채점 (옛 코드) | P50 + 1.63σ (95분위) | 없음 | **항상 ±3% 고정** |

- 958건 **전부** 금액이 달랐습니다. 차이 중앙 **393,662원(+0.43%)**, 최대 1억 732만원
- 판정이 **119건(12.4%) 뒤집혔습니다**
- 채점 화면이 보고한 실격률 **3.24%** ↔ 실제 추천의 실격률 **11.59%** (3.6배 과소보고)
- 동시에 1순위 획득률도 1.57% ↔ 실제 4.07% 로 과소보고 — 어느 방향으로도 틀렸습니다

**고침**: `sjSigma()` 와 `recommend()` 두 함수를 만들어 **추천과 채점이 같은 함수를 호출**합니다
(`BaroBid.jsx` 상단, export). 그리고 `bidresult.json` 에 예가범위(`lo`,`hi`)를 실어
채점도 그 공고의 진짜 범위를 씁니다.

## 8. 「사정률이 이 값이었다면」 표

소장님 지적: *"3% 차이가 나는데 하나의 가격으로 낙찰가랑 비교하는 게 잘못 아닌가"* — 맞습니다.

팀 검증 결과 **958건 100%가 「추첨에 따라 갈림」** 이었습니다.
(항상 통과 0건 / 항상 실격 0건 / p10~p75 통과·p90 실격 958건)
즉 통과·실격은 실력이 아니라 **그날 추첨이 정합니다.** 한 점만 보여주면 운을 실력으로 오해합니다.

그래서 채점 카드에 표를 넣었습니다 — 그 공고 자신의 분포(P50 + z×σ)로 만든 10개 자리 +

| 사정률 | 그때의 최저가(하한) | 우리 금액과 | 결과 |
|---|---|---|---|
| 98.631% (5분위) | 400,579,860 | +841만 | 통과 |
| … | | | |
| 99.720% ← **이번 개찰** | 404,976,623 | +402만 | 통과 |
| … | | | |
| 100.412% (75분위) | 407,772,473 | +122만 | 통과 |
| 100.690% (85분위) | 408,895,183 | +10만 | 통과 |
| 101.157% (95분위) | 410,781,174 | −179만 | **실격** |

⚠️ 후보를 «전국 사정률 10분위(`ov.sjc`)»로 쓰면 안 됩니다 — 전국 값에는 ±2%와 ±3%가
섞여 있어 ±2% 공고에서 있지도 않은 넓은 흔들림을 보여주게 됩니다.
**그 공고 자신의 분포**를 씁니다.

## 9. 채점 범위를 7일 → 7주로

`bidresult.json` 은 최근 **7일**치만 담는데 1순위 목록은 **7주**치를 보여줍니다.
그래서 6주치는 채점 버튼을 눌러도 아무 일이 안 일어났습니다.

**고침**: 1순위 카드가 채점에 필요한 값(`amt` `rate` `base` `aval` `ayn` `lo` `hi` …)을
**주소에 실어** 보냅니다. 자료를 한 바이트도 더 받지 않고 7주 전체가 채점됩니다.
(연락처·대표자는 색인에만 있어 지난 개찰에서는 «7일이 지난 개찰이라 연락처는 없습니다»로 표시)

# 추가 2 — 「같은 표·같은 계산」과 파라미터 재검증

## 11. 바로투찰과 채점이 이제 문자 그대로 같습니다

- 금액: `recommend()` 하나 — 두 화면이 같은 함수를 부릅니다
- 표: `buildScen()` + `<ScenTable>` 하나 — **앞으로 넣을 공고 화면과 채점 화면이 같은 표**
- 채점 카드에 «이 금액은 바로투찰이 그날 내놨을 금액과 같은 함수로 계산했습니다 —
  사정률 75분위 · 예가범위 -3%~3% · 여유 0.3%» 를 명시
- 앞으로 넣을 공고 화면에도 «이 표는 채점할 때 보여드리는 표와 똑같습니다» 안내

## 12. 「최대한 낙찰가와 차이가 안 나게」 — 재검증 결과: **지금이 최선입니다**

958건 전체로 사정률 기준을 훑었습니다.

| 사정률 기준 | 실격 | 1순위 | 낙찰가 차이(중앙) |
|---|---|---|---|
| 50분위 | 48.0% | 3.13% | 0.42% |
| 69분위 | 29.0% | 3.13% | 0.59% |
| 75분위 | 23.8% | 2.82% | 0.67% |
| **75분위 + 0.3% 여유** | **11.6%** | **4.07%** | **0.87%** ← 지금 |
| 84분위 | 14.6% | 3.24% | 0.83% |
| 90분위 | 8.2% | 2.51% | 0.99% |
| 95분위 | 3.7% | 1.88% | 1.19% |

**차이를 줄이는 것 자체는 목표가 아닙니다.** 50분위로 내리면 차이는 0.42%까지
줄지만 둘에 하나가 실격이고, 1순위가 되는 비율은 오히려 **떨어집니다**(3.13% ↔ 4.07%).
실격한 투찰은 싸게 쓴 것이 아니라 버린 것입니다.

1순위 비율의 표준오차는 ±0.5%p 라 2.5~4.1% 는 통계적으로 구분되지 않습니다.
지금 자리가 그중 가장 높고, 실격률도 낮은 편입니다. **바꿀 이유가 없습니다.**
